## 스토리별 결과

### 3-1: Railway 배포 및 환경변수 구성 ✅
- `backend/Procfile` 신규 생성, `$PORT` 바인딩으로 Railway 배포 성공
- 백엔드·프론트엔드·PostgreSQL 세 서비스 생성 완료
- CORS(`ALLOWED_ORIGINS`) 환경변수 방식으로 Railway URL 유연하게 적용
- **특이사항:** 코드 변경(Dev Agent) + Railway 대시보드 수동 작업(Catty) 이원화 방식으로 진행

### 3-2: 검색 품질 검증 및 최종 배포 승인 ✅ (조건부 통과)
- 25개 질문 테스트 시트 작성 및 테스트 수행
- 초기 정확도: 5/25 = **20%** (NFR-6 기준 80% 미달)
- 주요 원인: 한국어 어휘 불일치 (결석↔결시, 불만↔이의신청 등)
- 결정: 하이브리드 검색을 신규 스토리(3-3)로 분리하여 개선 추진

### 3-3: 하이브리드 검색 개선 (BM25 + 벡터) ✅
- `rank-bm25==0.2.2` 추가, RRF(Reciprocal Rank Fusion) 구현
- 정확도: **59%**로 향상 (20% 대비 3배 개선)
- 단위 테스트 15개 + 전체 회귀 60개 통과
- 코드리뷰: `_expand_query()` 예외 미처리 버그 발견 및 수정
- 이용 가이드 팁 UI 추가 (공식 용어 안내)

## 잘 된 점 (Strengths)

1. **Railway 배포 간결함**: Dockerfile 없이 Nixpacks 자동 감지로 백엔드·프론트엔드 모두 배포 성공. `Procfile` 한 파일로 해결.

2. **수치 기반 품질 측정**: 25개 질문 테스트 시트 덕분에 "나아진 것 같다"가 아닌 "20% → 59%"라는 구체적 수치로 품질을 추적할 수 있었음.

3. **코드리뷰 버그 발견**: `_expand_query()` 예외 미처리 — 운영에서 터졌으면 모든 채팅 요청이 HTTP 500으로 실패했을 버그를 배포 전에 잡음.

4. **실용적 의사결정**: 80% 미달이지만 이용 가이드와 함께 배포하는 결정. 완벽을 기다리는 것보다 현실적인 가이드라인 제공이 더 나은 UX.

5. **단계별 문제 해결**: 임계값 튜닝 → query expansion → 하이브리드 검색 순서로 체계적으로 접근. 각 단계에서 배운 점이 다음 시도에 반영됨.

---

## 어려웠던 점 (Challenges)

1. **근본 원인 파악이 늦었음**: 벡터 임계값 조정(0.5→0.75→0.82)과 query expansion을 먼저 시도하다가, 결국 BM25 도입이 필요하다는 걸 늦게 깨달음. 초기 기획 단계에서 한국어 어휘 불일치 문제를 미리 고려했어야 했음.

2. **코드 배포 ≠ 데이터 배포**: Railway 앱 재배포 후 DB 데이터는 그대로 유지됨 — 이를 간과하여 PDF 재업로드 없이 테스트, 낮은 초기 결과가 나온 원인 중 하나.

3. **한국어 형태소 한계**: 공백/구두점 단위 BM25 토크나이징으로는 "이의신청은" ≠ "이의신청" 문제 미해결. 정확도 59% 이상의 개선에는 형태소 분석기(KoNLPy 등)가 필요.

4. **배포 후 수동 검증 부담**: PDF 업로드, 25개 질문 테스트 모두 Catty가 직접 수행해야 하는 수동 작업. 자동화 가능한 영역이 남아 있음.

## 핵심 학습 (Key Learnings)

### 기술적 학습
1. **한국어 RAG = 하이브리드 검색이 기본**: 벡터 단독 검색은 공식 용어↔일상 표현 간격을 메울 수 없음. 키워드(BM25) + 벡터를 처음부터 함께 설계할 것.

2. **외부 API 호출 = try/except 필수**: OpenAI, 외부 서비스 호출 직후에는 항상 예외 처리 + 원본 값 폴백 패턴 적용.

3. **pgvector SIMILARITY_THRESHOLD 제거의 영향**: threshold 없이 항상 TOP_K 반환 시, GPT 시스템 프롬프트가 유일한 환각 방지 수단이 됨. 설계 시 이 트레이드오프를 인식하고 결정할 것.

### 프로세스 학습
4. **배포 체크리스트**: 앱 재배포 후 → DB 데이터 확인(PDF 업로드 상태) → 기능 테스트 순서를 체크리스트화.

5. **수치 기반 품질 기준의 중요성**: NFR-6(80%)처럼 명확한 수치 기준이 있으면 "좋은지 나쁜지"를 주관 없이 판단 가능. 다음 프로젝트에도 초기 기획 시 품질 기준 수치화 필수.
